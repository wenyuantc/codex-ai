# 测试员自动化闭环

## Goal

让 **测试员（tester）** 进入任务主链路：开发/修复完成后能自动生成或更新验收标准、执行验证、结果回写任务状态；失败则回流执行人修复，通过则进入下一阶段（与现有 `review_fix_loop` / 协调员流水线兼容）。

## Background

- 现状：角色含 `tester`；`ai_generate_tester_acceptance` 可生成验收清单；**没有**「任务完成后自动跑测」状态机 phase。
- 现有自动化：`review_fix_loop_v1`（审核→修复循环）、协调员 pipeline（优先于 review_fix）。
- 约束：兼容 local + SSH；活动日志中文；DB migration 如需新表/字段。

## Key Decisions

| 决策 | 结论 | 日期 |
|------|------|------|
| MVP 验证形态 | **混合模式**：项目可配置测试命令自动执行 + 测试员 AI 生成/更新验收清单；失败回流执行人 | 2026-08-05 |
| 流水线位置 | **先测后审**：开发结束后先测试员验收，通过后再进入 code review / review_fix | 2026-08-05 |

## Requirements

### R1 验收产物

- 任务可关联「验收清单」（测试员 AI 生成或用户编辑）。
- 清单可预览/编辑；大文本用 Monaco。
- 生成入口复用并增强现有 `ai_generate_tester_acceptance`。

### R2 项目测试命令

- 项目级（或全局默认 + 项目覆盖）可配置测试命令，例如 `npm test` / `cargo test`。
- local：在工作目录/任务 worktree 执行；SSH：在远程对应目录执行。
- 捕获 exit code、stdout/stderr 摘要（长度上限，完整日志可落会话或附件策略在 design 定）。

### R3 混合验证语义

- 一次「运行验收」至少包含：
  1. （可选若清单为空）AI 生成/刷新验收清单
  2. 执行配置的测试命令（若已配置）
  3. （可选）测试员 AI 对照清单 + 命令结果给出通过/失败结论
- **硬失败**：测试命令非 0 → 验收失败，不依赖 AI「嘴硬通过」。
- **无命令时**：仅 AI 清单验收仍可运行，但 UI 提示「未配置客观测试命令，结果偏主观」。

### R4 自动触发与手动

- 支持手动「运行验收」。
- **默认自动路径（先测后审）**：开发执行会话成功结束（或进入「待验收」）→ 测试员阶段 → 通过后才进入 `review` / 启动 `review_fix_loop`。
- 设置项：启用/禁用测试员自动化；失败回流策略；是否允许无测试命令时仅 AI 验收。

### R5 与现有自动化协作

- 扩展而非推翻现有状态机：在 review 之前插入 `tester` phase（命名在 design 定）。
- 协调员 pipeline 若存在：在「实现完成」之后、「审核」之前插入验收；冲突规则 design 写清。
- 无测试员：可配置跳过测试阶段直接审，不卡死主流程。
- 无测试命令且禁止仅 AI 验收：跳过或阻止并中文提示。

### R6 可观测

- 活动日志：`task_tester_*` 系列 action + 中文 label（仪表盘）。
- 任务卡/详情展示测试状态徽章（未跑/通过/失败/运行中）。

## Acceptance Criteria

- [ ] 配置了测试命令的项目：命令失败 → 任务失败回流且不可被 AI 单独标为通过
- [ ] 可生成/编辑验收清单，并在详情中查看最近一次验收结果摘要
- [ ] 手动「运行验收」全流程可完成
- [ ] 自动路径遵循先测后审：测试未通过不得进入自动 code review
- [ ] SSH 项目可跑远程命令或给出明确中文错误
- [ ] 活动中文；`npm run build` + `clippy -D warnings`；状态转移有 Rust 单测

## Out of Scope

- 云端 CI（GitHub Actions）深度集成
- AI 自动向仓库提交长期维护的测试代码套件
- 替换现有 review_fix_loop 为全新总状态机（应扩展而非推翻）
- 审核与测试完全并行（未选方案）
