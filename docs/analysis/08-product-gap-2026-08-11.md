# 08 · 产品缺口分析（2026-08-11）

> 分析日期：2026-08-11 · 基线：`docs/analysis` 00–07 / 应用 v0.5.6
> 对照区间：`7b3a6f6..2dbdb4a`（P0–P3 产品波次 + send_input + i18n + 报表 R1 全部落地后）
> 方法：**代码实读**（文件:行号可复核），不采信文档陈述、不按命名推断
> 视角：产品经理 —— 回答「这个项目还需要什么功能」

## 0. 结论（先读这段）

1. **功能闭环已通，功能密度很高**。218 个 IPC 命令、24 张表、44 个迁移、366 个 Rust 测试。`TASK.md` 的 P0–P2 基本全绿，P3 的 `send_input` / i18n / 报表也已落地。
2. **主矛盾已经换了**。不再是「能不能做」，而是：
   > **AI 跑起来之后，用户看不见成本、管不住并发、复用不了经验。**
3. **最大空白是成本可见性**。`codex_sessions` 表**没有任何 token 消耗列**；全库唯一解析 usage 的地方是 Grok 的一个日志摘要函数，不落库、不聚合、无 UI。一个「让 AI 替你干活」的产品，用户不知道一件活花了多少钱。
4. **并发处于裸奔状态**。产品明确支持员工多任务并发，但后端 grep `semaphore` / `max_concurrent` / `cron` **零命中** —— 没有上限闸门，也没有排队能力。
5. **文档已在对读者撒谎**。`README.md` 的引擎能力矩阵与 `app/database.rs` 的真源直接矛盾；表数/迁移数/命令数/测试数四项计数全部过时。这个项目本身供 AI agent 使用，文档失真的代价被放大。

**一句话**：能力面已经够厚，下一刀应该切向 **可度量（成本）+ 可批量（队列）**，而不是继续加功能。

## 2. 缺口清单（按产品价值排序）

### A. 运营可见性 —— 最大空白

#### A1 · Token / 成本零可见性 ⭐⭐⭐

**代码证据**：

- `src-tauri/src/db/migrations.rs:229` 建表 `codex_sessions`，字段为 `id / employee_id / task_id / project_id / cli_session_id / working_dir / status / started_at / ended_at / exit_code / resume_session_id / created_at`。
- 后续 8 处 `ALTER TABLE codex_sessions` 追加的是 `session_kind`（:325）、`execution_target` / `ssh_config_id` / `target_host_label` / `artifact_capture_mode`（:463–472）、`task_git_context_id`（:646）、`ai_provider`（:889）、`thinking_budget_tokens`（:897）。
  **注意 `thinking_budget_tokens` 是推理预算上限（配置项），不是实际消耗。**
- `codex_session_events`（`migrations.rs:244`）只有 `event_type` / `message` 两个业务列。
- 全库唯一解析 usage 的位置：`src-tauri/src/grok/process/stream.rs:812 summarize_usage()`，配合 `:799 usage_u64()` 读取 `input_tokens` / `output_tokens` / `total_tokens` / `reasoning_tokens`，然后在 `:978` 的 `Some("usage")` 分支把它**拼成一行文本刷进日志** —— 不落库、不聚合、无 UI。
- Codex / Claude / OpenCode 三个引擎的 `process/stream.rs` **连解析都没有**。

**用户痛点**：一个任务花了多少钱？哪个引擎性价比高？哪个员工在烧钱？跑一晚上账单会不会爆？全部无法回答。

**为什么是 P0**：这是**唯一无法通过其他途径获得**的数据——用户不可能从 4 个 CLI 的滚动日志里手工汇总。它也是选引擎、选模型、判断「这活值不值得让 AI 干」的唯一客观依据。产品已有 `employee_metrics`（完成数 / 平均耗时 / 成功率），唯独缺成本这一维。

---

#### A2 · 会话日志不可导出 / 不可复制 ⭐⭐

**代码证据**：`src/components/codex/CodexTerminal.tsx` 具备虚拟化（`:13 VIRTUALIZE_THRESHOLD = 80`）、外部关键词过滤（`:22 lines?` prop）、清空按钮（`Eraser`）、会话输入条（`SessionInputBar`）。但 grep `clipboard|writeText|复制|导出|下载` 在该文件及 `TaskLogDialog.tsx` / `SessionsPage.tsx` **全部零命中**。

**用户痛点**：AI 跑挂了，用户想把日志发给同事或贴进 issue，只能截图。

**成本**：极小——终端头部加两个按钮。

---

### B. 规模化执行 —— 从「一次一个」到「批量跑」

#### B1 · 无并发闸门 / 无运行队列 / 无调度 ⭐⭐⭐

**代码证据**：全库 grep `cron` / `schedule` / `semaphore` / `max_concurrent` / `concurrency` —— 后端**零命中**（唯一命中是 `src/lib/ai.ts:28` 的一个中文关键词匹配，与调度无关）。`app/tasks.rs:439` 的注释提到 `send_input` 可以 queue，但那是单会话内的输入排队，不是任务级队列。

而 `TASK.md:98` 记录「员工需要支持多任务运行」已实现，`01-domain-capability-matrix.md` §3 也标注「多任务并发运行 ✅」。

**两层缺口**：

1. **上限缺失** —— 同时点 5 个任务 = 同时 5 个 AI CLI 进程。本机 CPU / 内存 / 上游 API 限流全部裸奔，没有任何闸门。
2. **排队缺失** —— 不能「把 8 个任务排好，晚上自动依次跑完」。用户必须守着手动点。

**为什么是 P0**：这是把工具从**手动挡**变成**自动挡**的关键，也是本产品相对「自己开 4 个终端跑 CLI」的最大差异化。当前状态下，用户用得越重越容易翻车。

---

#### B2 · 无任务模板 ⭐⭐

**代码证据**：`src-tauri/src/codex/prompt_templates.rs:9` 的 `PROMPT_TEMPLATES_FILE_NAME = "ai-prompt-templates.json"` 存的是 **AI 功能的提示词模板**（「生成 commit message 用什么 prompt」），与任务模板无关。全库无 `task_template`。

**用户痛点**：重复性任务（「给这 20 个模块补 i18n」「给每个 API 加单测」）要手工建 20 次任务、写 20 遍描述。

**已有可复用基础**：

- `app/tasks.rs:1710 batch_update_tasks`（批量改状态，`:1718` 限制单次 100 个）
- `app/tasks.rs:2263 export_tasks_json` / `:2560 import_tasks_json`（版本化 envelope，含依赖边，`app/tests/tasks_json.rs` 有 roundtrip 测试）

模板机制可直接复用这套 JSON 结构，不必另起炉灶。

---

### C. 审查深度 —— 目前太粗

#### C1 · 审查只有整体 verdict，没有行级定位 ⭐⭐

**代码证据**：全库 grep `line_comment` / `inline_comment` / `行级` **零命中**。`app/review.rs`（1165 行）解析的是 verdict（通过/不通过）+ 阻塞问题数 + 摘要。

**用户痛点**：AI 说「不通过，3 个阻塞问题」，用户得自己翻 diff 找是哪 3 行。

**已有基础**：`codex_session_file_change_details` 表已存 diff 明细；Monaco 已接入（`src/lib/monaco.ts`）。缺的是把审查输出结构化成 `{file, line, severity, message}` 并锚定到 diff 视图。

---

#### C2 · 无 hunk 级暂存 ⭐

**代码证据**：Git 工作流是文件粒度（`stage_file` / `stage_all`），无 `git add -p` 等价物。

**判断**：**建议不做**。AI 场景下「整文件接受 / 回滚」是主流操作，hunk 级收益低、实现成本高（需自研 patch 编辑器）。已写入 `TASK.md` 的明确不做清单。

---

### D. 产品化基础设施

#### D1 · 无自动更新 ⭐⭐

**代码证据**：`src-tauri/Cargo.toml:17-30` 的 Tauri 插件只有 `opener` / `sql` / `shell` / `dialog` / `notification` —— **无 `tauri-plugin-updater`**；`tauri.conf.json` 无 updater 段。

**用户痛点**：`.github/workflows/build.yml` 已在 tag 推送时打好三平台安装包，但用户装完之后**永远不知道有新版**，得自己去 GitHub 翻 Releases。发版链路的最后一公里断了。

**成本**：小——加插件 + `latest.json` + 设置页「检查更新」入口。

---

#### D2 · 文档与代码已漂移 ⭐

**三处硬伤**：

1. **引擎能力矩阵与代码矛盾**：`README.md:91-96` 写 Claude / Grok / OpenCode 的「会话中发送输入」全是 ❌，但 `src-tauri/src/app/database.rs:833`（Claude）与 `:843`（OpenCode）的 `send_input` **已是 `true`**（commit `2aac559` 落地，且有 `capability_matrix_is_honest_and_complete` 单测守护，`database.rs:900-907`）。只有 Grok 的 `false`（`:853`）仍然正确。
2. **计数失真**：`README.md:162` 说「22 张表 / 80 个迁移」→ 实际 24 表 / 44 迁移。README 的表清单也确实只列了 22 张，漏掉 `task_pipeline_steps`（协调员流水线步骤）与 `task_acceptance_runs`（测试员验收记录）。
3. **计数失真**：`CLAUDE.md` 说「207 命令 / 339 Rust 测试 / 前端 32 断言 4 文件」→ 实际 218 / 366 / 104 断言 9 文件。且各模块分项也已过时（`codex/` 实为 30 非 28、`claude/` 11 非 8、`opencode/` 12 非 9、`task_automation` 12 非 10）。
4. **整个模块未被任何文档记录**：`src-tauri/src/app/session_events_retention.rs` 提供 4 个命令（`get_session_events_policy` / `update_session_events_policy` / `get_session_events_stats` / `purge_session_events`），实现 `codex_session_events` 的按天保留策略、`VACUUM` 与统计。README 的「数据库维护」段与 `CLAUDE.md` 的模块清单**都没有提到它**。

**影响**：新人和 AI agent 读文档建立的是**错误**心智模型——不只是数字偏差，还包括「以为不存在的能力其实已经有了」（如会话事件保留策略）。本项目本身就是给 AI agent 用的，文档失真的代价被放大。

> 本轮已修正（见 §5）。

## 3. 优先级建议

RICE 视角（覆盖面 × 影响 / 成本）：

| 级别 | 项 | 核心理由 | 成本 |
|---|---|---|---|
| **P0** | A1 成本可见性 | 唯一无法替代获取的数据；产品差异化核心 | 中 |
| **P0** | B1 并发闸门 + 队列 | 当前裸奔，用户越用越容易翻车 | 中 |
| **P1** | A2 日志导出 | 成本极低、痛点高频 | 极小 |
| **P1** | D2 文档校准 | 极低成本，止住持续误导 | 极小（本轮已做） |
| **P1** | D1 自动更新 | 一次投入长期收益，CI 已就绪 | 小 |
| **P2** | B2 任务模板 | 场景明确，需设计变量机制 | 中 |
| **P2** | C1 行级审查 | 提升审查质量，需改 AI 输出契约 | 中大 |
| **P3** | E1 组件拆分 | 无用户可见收益，但阻塞后续任务侧迭代 | 大 |
| **不做** | C2 hunk 暂存、外部 Issues 同步、第五引擎 | 与既有决策一致 | — |

## 4. 建议的下一波方案（供排期，本轮未实现）

**主题：让「AI 干活」这件事变得可度量、可批量。**

三件事讲一个完整故事 —— *用户把一批任务排队丢给 AI，跑完知道花了多少钱，出问题能把日志捞出来*。

### 4.1 A1 成本可见性

| 层 | 动作 |
|---|---|
| 数据层 | 新增 migration v45，给 `codex_sessions` 加 `input_tokens` / `output_tokens` / `total_tokens` / `reasoning_tokens`（均 nullable，**无值即未知，不假装 0**） |
| 引擎层 | 四个 `process/stream.rs` 各自解析 usage 事件。Grok 已有 `summarize_usage()` / `usage_u64()` 可直接复用取值逻辑；Codex / Claude / OpenCode 需新增解析，**解析不到就留 NULL** |
| UI 层 | 任务详情「执行」Tab 显示本任务累计 token；仪表盘扩展 `get_dashboard_report_summary`，加「近 7/30 天 token 趋势 + 按引擎/员工分组」 |

关键文件：`src-tauri/src/db/migrations.rs`、`src-tauri/src/{codex,claude,grok,opencode}/process/stream.rs`、`src-tauri/src/app/database.rs`、`src/components/tasks/detail/`、`src/pages/DashboardPage.tsx`

**诚实边界**：token 数只是**用量**，换算成金额需要单价表，且各引擎计费口径不同。建议一期只做 token 用量，不做金额估算，避免给出误导性数字。

### 4.2 B1 并发闸门 + 运行队列

| 层 | 动作 |
|---|---|
| 闸门 | `src-tauri/src/engine/` 共享内核（`ProcessManager` / `EngineProcessRegistry`）加全局并发上限，设置页可配（默认建议 2–3） |
| 队列 | 超出上限的启动请求进入排队，而非直接失败或裸并发；看板卡片显示「排队中（第 N 位）」 |
| 批量 | 复用现有 `batch_update_tasks` 的选中机制，加「批量运行选中任务」 |

关键文件：`src-tauri/src/engine/`（**先改共享内核**，符合 `CLAUDE.md` 的既定原则）、`src-tauri/src/app/tasks.rs`、`src/components/tasks/KanbanBoard.tsx`

**注意**：队列状态需持久化，否则重启丢失——参照 `task_automation_state` 的 resume 模式（`TASK.md` 历史条目里编排失败状态重启丢失就是同类问题）。

### 4.3 A2 日志导出

`CodexTerminal.tsx` 头部加「复制全部 / 导出 .log」，复用已有的 `lines` 数据源。

## 6. 边界（明确不做）

沿用 `TASK.md` 既有路线图级决策，不推翻：

- 微服务拆分
- 远程多端实时同步
- 第五个 AI 引擎
- 完整 IDE 体验（LSP / 调试器）
- Jira / GitHub Issues 双向实时同步

本轮新增：

- **hunk 级暂存（C2）** —— AI 场景下整文件接受/回滚是主流，自研 patch 编辑器成本高、收益低
- **token → 金额换算** —— 各引擎计费口径不同，一期只做用量，不给误导性金额
